# Как бот соединён с остальным проектом

Бот держит у себя хаб моста, поэтому через его процесс проходит не только
Telegram, но и выдача доната с сайта. Здесь описано, кто с кем разговаривает.

## Мост: кто к кому подключается

```
grief / vanilla / stolby / lobby   (GoPlayBridgeBackend + GoPlayTelegram)
        │ TCP, построчный JSON
        ▼
Velocity (GoPlayBridge) ──WSS──► бот на Railway, src/bridge/server.ts
                                        ▲
                        go-play-be ─────┘  WSS, роль "api"
```

Хаб внутри бота слушает тот же порт, что и HTTP. Наружу инициатив не проявляет:
и прокси, и бэкенд сайта подключаются к нему сами.

Кадры протокола (`src/bridge/protocol.ts`):

| Тип | Кто шлёт | Смысл |
|---|---|---|
| `auth` | клиент | секрет `BRIDGE_SECRET` и роль `bridge` или `api` |
| `request` | бот или `api`-клиент | консольная команда на сервер |
| `response` | `bridge`-клиент | результат с захваченным выводом консоли |
| `query` | бот | запрос данных по теме, ответ может прийти позже |
| `queryResult` | `bridge`-клиент | ответ на запрос |
| `event` | `bridge`-клиент | событие, которого никто не запрашивал |
| `ping` / `pong` | оба | keepalive на TCP-участке |

Роль `bridge` может быть только одна: новое подключение вытесняет старое.
Ролей `api` может быть сколько угодно.

Незнакомый тип кадра игнорируется молча в обе стороны, поэтому порядок
обновления бота, прокси и режимов значения не имеет.

Темы запросов обслуживает плагин `GoPlayTelegram`: `link.redeem`, `resolve`,
`stats`, `top`, `scan`, `ref.bind`.

## Выдача доната с сайта

Это единственный путь, которым привилегии попадают к игроку. Бот в нём
работает транспортом и ничего не решает.

```
оплата на go-play.gg
  → go-play-be, shop.service.ts deliverOrder()
  → bridge.service.ts execute(order.server, command)   роль "api"
  → хаб бота, forwardApiRequest()
  → GoPlayBridge на Velocity
  → нужный сервер, команда из variant.commands с подстановкой {player}
```

Отсюда два следствия:

- Бот лежит — донат не выдаётся. При редеплое лучше не иметь незакрытых оплат.
- В заказе указан конкретный сервер, привилегия выдаётся на один режим.
  Базы LuckPerms на серверах независимые, общего ранга по сети не существует.

Ломать этот путь нельзя. Роль `api`, пересылку `request`/`response` и секрет
трогаем только вместе с `go-play-be`.

## Рассылка анонсов

`POST /notify` на публичный порт моста, заголовок `x-notify-secret`,
тело `{"text": "<HTML>"}`. Включается только при заданном `NOTIFY_SECRET`.

```bash
curl -X POST "$URL/notify" \
  -H "x-notify-secret: $NOTIFY_SECRET" \
  -H "content-type: application/json" \
  -d '{"text":"🪂 Айрдроп <b>Амбар</b> появился. Спешите за лутом."}'
```

Отвечает `202` сразу, рассылка идёт в фоне. Текст до 8192 символов, иначе `413`.
Битый HTML не роняет рассылку: сообщение уйдёт без разметки.

Адресаты — все, у кого включена тема `announce`. Отправкой занимается общая
очередь (`src/push/queue.ts`): общий темп около 25 сообщений в секунду, не чаще
одного в 1.1 секунды на чат, соседние события склеиваются в одно сообщение.
Заблокировавшие бота вычищаются из подписок автоматически.

Здоровье: `GET /health` или `/` отдаёт `{"status":"ok","bridgeConnected":…,"apiClients":…}`.

## Хранилище

SQLite (`bun:sqlite`) в файле из `DATABASE_FILE`. В Docker это `/data/goplay.db`,
и без постоянного диска на `/data` данные не переживут редеплой. На Railway это
Volume с mount path `/data`; директиву `VOLUME` в Dockerfile там объявлять нельзя,
сборка упадёт.

Таблицы: `links` (привязка Telegram к игровому аккаунту), `subscriptions`
(темы уведомлений), `push_log` (что уже отправляли, чтобы не слать дважды),
`players` (кеш «ник в UUID»), `stat_cache` (последний удачный ответ сервера),
`pending_refs` (кто кого позвал, до привязки аккаунта) и `stat_snapshot`
(срез цифр на начало недели для дайджеста).

## Чего в боте нет

- Платежей и выдачи привилегий. Продажа живёт на сайте, бот только транспорт.
- Админских команд. Для консоли есть панель Pterodactyl.
- AI-ассистента. Удалён.
